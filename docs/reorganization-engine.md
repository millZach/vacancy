# Isolated Windows reorganization engine

This is a core-library milestone. Vacancy does not expose reorganization or Undo controls yet. There is no live advisor integration; metadata-only fake proposals remain separate from execution authority. Non-Windows inventory and mutation entry points return `Unsupported` before accessing the filesystem.

`Inventory::capture` takes a fresh capped metadata inventory of loose, top-level regular files in Downloads, Desktop and Documents. It does not assert that its entries came from an earlier disk-map scan. A `Draft` refers to an opaque inventory entry and native destination components; validation fixes the complete names, including collision suffixes, into a `ValidatedPlan`. Public review strings are escaped display text, not paths granting filesystem authority. Existing directories and roots are not move sources. Aliased or nested known-folder roots and cross-volume moves are unsupported.

A trusted caller retains the original approval and passes the validated capability to `Engine::begin`. The caller supplies an existing ordinary AppData directory inside the sealed same-volume root, and a journal leaf directly in that directory. The AppData identity is not itself sealed into the plan. The engine binds its storage parent to the approved root, acquires the complete no-follow native parent chain and an exclusive stable journal lease, then durably records the approved plan. It rechecks source identity, fingerprint, allocation, link count and Guard authority before a same-volume, handle-relative rename. Destinations are never overwritten; there is no copy/delete fallback. Each namespace mutation (move, mkdir, Undo or owned-directory removal) has a flushed intent before mutation and a durable result afterward. Failure to record a result stops further mutations and can leave an unresolved intent.

The engine owns the exclusive lease until it is dropped. `Engine::open` requires an existing valid lease and reads evidence. It does not create or repair a lease, resume moves, remove directories, or undo anything automatically. `reconcile` may append observations of a pending operation without moving userdata. An explicit `run` can start that same originally approved durable manifest only before its durable `Started` record exists. A previously started run never resumes: `run` returns status when no intent is pending, or `Unresolved` otherwise. Retaining the original approval is a trusted-caller obligation; `open` does not obtain new consent. No app Resume policy is implied. `undo` runs explicitly in reverse, preserving same-file edits while refusing conflicts, replacements and ambiguous hard links. Only still-identical empty directories positively created by this run may be removed.

The journal keeps native exclusive handles and append-only segments with bounded, checksummed framing and continuation bindings. Torn bytes remain preserved; a continuation binds preceding segment identities, full-byte digests and committed sequence. Complete malformed or impossible records fail closed. The store allows at most 32 segments and 32 MiB. A corrupt, unavailable or exhausted store may prevent further reconciliation or Undo. File flushes and process-crash tests do not establish power-loss atomicity, directory-entry persistence or hardware-cache behavior.

`Status::skipped` counts operation receipts across forward moves, directory operations and Undo. It must not be shown as a count of skipped files. The current public API uses `Changed` for both fingerprint mismatch and a source open rejected by sharing; it has no per-entry reason mapping.

After an admitted successful run and an independent audit of its saved evidence, the opt-in `reorg_fixture` example can demonstrate a bounded core round trip. It requires `--run` and two existing empty, nonoverlapping profile/evidence directories outside home, with conservative ASCII drive paths. `VACANCY_FIXTURE_ROOT` must match the profile argument exactly. Never run it on a real home or drive. Its saved manifests compare names, kinds, lengths and FNV content summaries, with native IDs for selected seeds and their hard-link peer. This is separate from installed-app, UI, ACL/timestamp, all-writes, power-loss and macOS acceptance. ADR0005 remains proposed.
