# Windows reorganization engine and Tidy up

The app's Tidy up (Windows only) runs on this engine. Its proposals come from built-in sorting rules in `crates/vacancy-core/src/tidy.rs`, offline, from names, sizes and dates: loose top-level files of Downloads, Desktop and Documents go into folders by kind (Images, Videos, Documents, Installers, Archives) and, for images, videos and documents, by the year they were last modified (UTC), with "Sort later" for the rest. Shortcuts, `desktop.ini`, unfinished downloads and hidden files stay. Each folder is one proposal, inventoried with `Inventory::capture_folder` (all three roots sealed, only that folder listed, at most 512 entries in its name order; a capped proposal says how many more files the scan counted). A file a delete proposal in the same plan takes is left out of the sort (delete wins). The plan validates each chosen sort again; the executor runs the sorts after the deletes, each folder with its own journal in the app data folder's `tidy` directory, and keeps a checkpoint report in the history before any file moves. Moves free 0 B. Undo, from the summary, the Moved slide or Past runs, opens the journal (also after a restart) and reports what came back, what couldn't and why, and which empty folders were removed; reopening a run reads its journals and may reconcile an unconfirmed intent, but never moves, removes or resumes anything. There is no live advisor integration and AI reorganization proposals stay deferred; metadata-only fake proposals remain separate from execution authority. Non-Windows inventory and mutation entry points return `Unsupported` before accessing the filesystem, and macOS shows no Tidy up.

`Inventory::capture` takes a fresh capped metadata inventory of loose, top-level regular files in Downloads, Desktop and Documents. It does not assert that its entries came from an earlier disk-map scan. A `Draft` refers to an opaque inventory entry and native destination components; validation fixes the complete names, including collision suffixes, into a `ValidatedPlan`. Every directory a draft names reserves that name (case-insensitively) at validation time, so a file destination never takes a name a planned directory will hold. Drafts are validated one at a time: an unknown, repeated or changed source, an invalid or Guard-refused name, a directory conflicting with another draft's, or a draft with no free name is dropped and listed in `ValidatedPlan::dropped` with its reason, while the other drafts are kept. A source named by more than one draft is dropped from all of them. The batch fails only for batch-wide reasons (bounds, cancellation, a replaced known folder, an oversized manifest), or when no draft is left, with the first dropped draft's error. Public review strings are escaped display text, not paths granting filesystem authority. Existing directories and roots are not move sources. Aliased or nested known-folder roots and cross-volume moves are unsupported.

A trusted caller retains the original approval and passes the validated capability to `Engine::begin`. The caller supplies an existing ordinary AppData directory inside the sealed same-volume root, and a journal leaf directly in that directory. The AppData identity is not itself sealed into the plan. The engine binds its storage parent to the approved root, acquires the complete no-follow native parent chain and an exclusive stable journal lease, then durably records the approved plan. It rechecks source identity, fingerprint (length, allocation, and the creation, last-write and change times each compared separately), link count and Guard authority before a same-volume, handle-relative rename. Destinations are never overwritten; there is no copy/delete fallback. Each namespace mutation (move, mkdir, Undo or owned-directory removal) has a flushed intent before mutation and a durable result afterward. Failure to record a result stops further mutations and can leave an unresolved intent.

The engine owns the exclusive lease until it is dropped. `Engine::open` requires an existing valid lease and reads evidence. It does not create or repair a lease, resume moves, remove directories, or undo anything automatically. `reconcile` may append observations of a pending operation without moving userdata. An explicit `run` can start that same originally approved durable manifest only before its durable `Started` record exists. A previously started run never resumes: `run` returns status when no intent is pending, or `Unresolved` otherwise. Retaining the original approval is a trusted-caller obligation; `open` does not obtain new consent. No app Resume policy is implied. `undo` runs explicitly in reverse, preserving same-file edits while refusing conflicts, replacements and ambiguous hard links. Only still-identical empty directories positively created by this run may be removed. A move refused because a directory took its destination name, with the file still at its source under the same identity, is skipped with a reason rather than left unresolved, so it never blocks Undo of other moves. A mkdir whose durable creation receipt was lost in a crash is reconciled as skipped: whatever holds that name is not claimed, never removed by Undo, reported as left in place, and does not block Undo.

The journal keeps native exclusive handles and append-only segments with bounded, checksummed framing and continuation bindings. Torn bytes remain preserved; a continuation binds preceding segment identities, full-byte digests and committed sequence. Complete malformed or impossible records fail closed. The store allows at most 32 segments and 32 MiB. A corrupt, unavailable or exhausted store may prevent further reconciliation or Undo. File flushes and process-crash tests do not establish power-loss atomicity, directory-entry persistence or hardware-cache behavior.

`Status::skipped` counts operation receipts across forward moves, directory operations and Undo. It must not be shown as a count of skipped files; the app reads `Engine::ledger`, a display-only record of each move, mkdir, Undo and directory removal with its recorded reason. A move whose source is open in another app (`InUse`), gone (`Gone`) or whose destination name is now taken (`Taken`) says so; other mismatches stay `Changed`. `run_observed` and `undo_observed` tell an observer how far they have got; the observer cannot change what runs.

After an admitted successful run and an independent audit of its saved evidence, the opt-in `reorg_fixture` example can demonstrate a bounded core round trip. It requires `--run` and two existing empty, nonoverlapping profile/evidence directories outside home, with conservative ASCII drive paths. `VACANCY_FIXTURE_ROOT` must match the profile argument exactly. Never run it on a real home or drive. Its saved manifests compare names, kinds, lengths and FNV content summaries, with native IDs for selected seeds and their hard-link peer. This is separate from installed-app, UI, ACL/timestamp, all-writes, power-loss and macOS acceptance. ADR0005 remains proposed.
