# 0008: Live Claude advisor through the user's Claude Code, with a privacy mode

Date: 2026-10-22. Status: accepted (Zach). Supersedes the Oct 17 deferral of CLI AI (`docs/advisor-status.md`) and narrows ADR 0003 to Claude Code only.

Zach turned live AI on. Vacancy calls the user's own Claude Code (`claude`), through their subscription. There is no Codex and no API key. AI is **off until the user turns it on**, after a privacy notice. The user can turn it off again any time.

## What Claude does

All of these appear in a docked Claude side panel (prototype `prototype/ai-advisor`, variant B):

- **Review my plan:** a second opinion that flags proposals it thinks are risky, with a reason. It adds nothing.
- **Let Claude pick:** one button and no goal. Claude ticks and unticks the rules' proposals and may add its own. The user sees the changes against their plan, then picks Keep mine or Use Claude's plan.
- **Ask Claude:** a follow-up chat about any proposal or folder: what it is, what you'd lose, whether it comes back.
- **Explain big folders:** big folders the rules don't recognize get an explanation. Any removable items Claude suggests are added to the plan unticked.
- **Suggest Tidy up layouts:** Claude's sorting of the loose files of Downloads, Desktop and Documents, with Sort later, as an alternative to the built-in layout. Moves stay journaled and undoable, and the 512-file cap, pinned names and delete-wins-over-sort still apply.

## What Claude can never do

- **Claude proposes; it never executes.** Its output is structured data. Every item it adds is marked "Suggested by Claude", starts unticked with risk Review, must point at something the scan saw, and must pass the Guard (ADR 0002). Invalid items are dropped and the reason is shown. The executor treats Claude's items like any other. Turning Claude off keeps its items already in the plan.
- **Only the scan it was about.** Every command that touches Claude's part of a scan names the scan its map came from: a job, a chat, Keep mine taking items out, and a layout picked. The core refuses it once the drive has a newer scan (or the plan ran, or the drive went away). Item ids like `claude-d17` come again in the next scan, so a command for a replaced scan must never touch the new one. The UI never starts one for a scan that is gone. Every complete map the core gives out for a scan carries one revision, counted per scan across the scan's own map (0), the duplicate search's and each Claude answer's. The UI shows a map only if its revision is above the one it shows, whichever kind each is, so a slow reply never puts back an older map. The duplicate search's end is kept apart from its map: a map refused as stale still ends the search. One Let Claude pick runs at a time: while one runs, the chip and every pick card's Try again wait, so the answers come in the order they were asked. The newest answered pick is the one whose answer came last (one set aside included). The panel keeps it the moment each answer is handled, never from what was last drawn, and that one pick decides both which card offers Keep mine and whose Keep mine may put the plan back. Keep mine puts the plan back only if, once its items are out, its card is still the newest answered pick and the plan is still as its answer left it; the drive's plan checks the pick's version and ticks as it puts the plan back.
- **Claude Code runs locked down.** The command is `claude -p --tools <set> --setting-sources "" --strict-mcp-config --disable-slash-commands --no-session-persistence --permission-prompts none --system-prompt <Vacancy's> --output-format json --json-schema <schema>`, with these settings:
  - It runs from an empty folder Vacancy owns.
  - `ANTHROPIC_API_KEY` is removed from its environment.
  - `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` are set.
  - `CLAUDE_CODE_DISABLE_ATTACHMENTS=1` and `CLAUDE_CODE_DISABLE_FILE_MENTIONS=1` are set in both modes, so an `@` path typed in a chat is never expanded into a file's contents (review of #29; `docs/proof/t12-attach-probes/`).
  - The always-hidden deny rules are passed with `--settings` in both modes: with privacy mode on, as defence in depth. The settings are a file Vacancy writes for each call, beside the call's empty folder (never in it) and removed with it, and the file denies itself; a command still over 30,000 UTF-16 units isn't started (`docs/proof/t12-settings-file-probe/`).
  - **The settings are checked before every call.** Claude Code stops at startup on a `--settings` file over 2 MiB (its docs), but a `-p` call given one that fails validation carries on without it, deny rules and all, with exit code 0, nothing on stderr and nothing in its JSON output to say so: a real probe read a canary its deny rule named (`docs/proof/t12-invalid-settings-probe/`). There is no cheap, reliable way to ask Claude Code afterwards whether it took the file, so Vacancy's own check is the guard. A file over 1.5 MiB, or holding anything but `permissions` with `Read(/...)` allow and deny rules (each on one line, at least one deny) and `blockReadsOutsideWorkingDirectories: true`, isn't started. With privacy mode off, a scan whose rules would be over 1.5 MiB (hundreds of browser profiles, each a set of rules of its own) runs every call as if privacy mode were on, and the answer and then the panel's privacy row say why; no rule is ever left out to fit. With privacy mode on, where Claude has no tools, such a scan's own browser rules are left out and the always-hidden list stays.

  So the user's hooks, plugins, MCP servers, CLAUDE.md files and settings don't load, and no transcript is kept. `--bare` can't be used because it never reads the subscription login.

## Privacy mode

- **On**, the default when Claude is turned on: `--tools ""`. Claude gets names, sizes, counts and dates from the scan only, never file contents.
- **Off** (the user's choice, after a confirm, and remembered): `--tools Read,Glob,Grep`. Claude can read files on the drive that was scanned, and on no other (Zach's decision). It still can't write, delete, run commands or go online. In fixture mode its reads are confined to the fixture folder (on a case-sensitive Mac volume, also to a sibling spelled like it in other case; see the known limit below).
  - **The scanned drive only.** `--add-dir` and the one allow rule name the scan's mount point, and the settings set `blockReadsOutsideWorkingDirectories`, so Claude Code refuses reads outside it by itself. Every other drive is also denied by rule (`runner::off_drive_rules_in`), because deny rules win, and Claude Code checks them against a link's target too (its permissions docs, "Symlinks"), so a junction or symlink on the drive that leads to another drive is refused as well. On Windows that is every other drive letter, plugged in now or later. On a Mac, scanning `/` covers the system volume and the Data volume that firmlinks show inside it (`/Users`, `/Applications`), and denies `/Volumes` (other disks, and `Macintosh HD`, a link back to `/`) and `/System/Volumes` (the rest of the container, and the Data volume's second name, `/System/Volumes/Data/...`, where the rules built from the scan's `/Users/...` paths wouldn't match). Scanning `/Volumes/X` allows `/Volumes/X` only: at `/` every child but `Volumes`, and at `/Volumes` every child but `X`, is denied (as far as the names are plain, as in a browser profile's rules). The other drives the drive list offers are denied by their mount points as well. The prompt, the system prompt, every answer's "based on" line ("Claude opened 3 files from the drive you scanned, like ..."), the privacy-off confirm ("Claude can open and read files on the drive you scanned, but not on your other drives") and the panel's privacy row all say so.
  - **Every other file system, wherever it is mounted** (review of #29). A file system mounted inside the scanned drive is another drive too: a read-only disk image of browser backups at `/Users/alex/Archive`, an NTFS volume or a VHD in the empty folder `C:\Mount\Disk2`. The scan stays on one file system, so it never went into it and no browser profile's rules were made for what it holds, while `--add-dir` and the allow rule name paths only, and `blockReadsOutsideWorkingDirectories` doesn't look at which file system a path is on. So right before each call Vacancy lists every place the OS says a file system is mounted, whatever the drive picker offers (`claude::mounts`: on macOS `getfsstat`, every mount, disk images and snapshots included; on Windows every volume from `FindFirstVolumeW` and each of its paths from `GetVolumePathNamesForVolumeNameW`, its letter and every folder it is mounted in), and denies each one whole, spelled as a deny rule spells a path (more, never less), except the scanned drive itself and a mount that holds it (`/` for `/Volumes/X`), whose way down is narrowed as above (`runner::mount_rules_in`). On a Mac a file system mounted inside the Data volume is denied by both its names (`/System/Volumes/Data/Users/alex/Archive` and `/Users/alex/Archive`). If the list can't be read whole, or a mount point can't be spelled as a rule at all (not from a drive letter or `/`, not Unicode, or cut short by the kernel), the call runs as if privacy mode were on, and the answer says why (a mount list that can't be read, in the panel's privacy row too); the settings would deny every read as a second wall.
  - **What that leaves:** a file system mounted after the list is read, while a call runs, isn't denied for that call (the next call's list has it). A link on the drive whose target is a volume by its GUID path (`\\?\Volume{...}\`, not a registered mount point) or a share isn't named by any rule; Claude Code checks a link's target against the working directory and the allow rule, which it is outside of, so the read needs a permission prompt, which `--permission-prompts none` refuses.
  - **Why it matters:** browser profiles are found from one scan's markers. With reads on every drive, a profile on a drive that wasn't scanned (`C:\BrowserData\Work` while `D:\` was) had only the by-name rules; now it isn't readable at all.
- **Always hidden, even with privacy mode off.** Vacancy passes Claude Code `permissions.deny` rules for Read, Glob and Grep, so Claude Code enforces them. Vacancy also never puts these places' contents in a prompt:
  - **keys and sign-ins:** SSH and GPG keys, cloud and developer tokens (.aws, .azure, gh, npm, Docker), `.env` files, Claude Code's and Codex's own folders (`~/.claude`, `~/.claude.json`, `~/.codex`, and wherever `CLAUDE_CONFIG_DIR` and `CODEX_HOME` move them; Vacancy never reads inside them), Windows Credentials and DPAPI Protect folders, the macOS Keychain;
  - **browser data:** browser profiles found by their marker files are hidden whole except their cache folders, plus by-name rules everywhere. That covers saved passwords and the keys that unlock them, cookies and site sign-ins and site storage, history, sessions and bookmarks, autofill and form history, extensions' own storage (where wallet extensions keep their vaults) and sync data, in Edge, Chrome, Brave, Vivaldi, Opera and other Chromium browsers (and Electron apps, which keep the same layout), Firefox and Safari (`Library/Safari`, as before). Zach approved hiding bookmarks, sessions and site storage with the rest.
    - **Markers** (`crates/vacancy-core/src/claude/browsers.rs`; the scan notes them for every folder, so finding profiles costs nothing, the normal scan and the fast scan alike, and for every name of a hard-linked file: a backup profile whose `Preferences` is a hard link to another profile's is a profile too, and hard links are merged for the byte totals only): a Chromium profile is a folder holding `Preferences` and at least one of `History`, `Login Data`, `Cookies`, `Web Data`, `Bookmarks`, `Secure Preferences` or a `Network` folder; a Firefox profile holds `prefs.js` and at least one of `times.json`, `places.sqlite`, `key4.db`, `cookies.sqlite` or `compatibility.ini`. A `Preferences` file alone (a game's settings) is no profile. The folder above a Chromium profile is its browser's root when it holds `Local State`, wherever `--user-data-dir` put it; so is each browser's default root the scan saw (Chrome, Edge, Brave, Vivaldi, Chromium, Yandex, Opera and Firefox on Windows, those and Arc on a Mac), where folders Chromium names as profiles (`Default`, `Profile *`, `Guest Profile`, `System Profile`) count as profiles without markers. A default root the scan didn't see is hidden whole.
    - **What stays readable:** in a Chromium profile or root, the cache folders the built-in rules propose there (`Cache`, `Code Cache`, `GPUCache`, `DawnCache`, `DawnGraphiteCache`, `DawnWebGPUCache`, `GrShaderCache`, `GraphiteDawnCache`, `ShaderCache`, `CachedData`), and in a root the way down to its profiles; in a Firefox profile, `cache2`, `startupCache`, `thumbnails`, `shader-cache` and `jumpListCache`. `Service Worker/CacheStorage` is a site's own store and no rule proposes it, so `Service Worker` is hidden whole. Everything else in a profile is hidden from Claude Code's tools, from every prompt, and from Claude's suggestions, and so is a suggestion to delete a profile or root whole.
    - **How the rules say it:** a deny rule always wins and the matcher has no negated patterns (`[!x]` means `!` or `x`), so each profile's rules spell the complement of its allowed names: patterns from a tree of those names, made of literal characters, `?`, `*` and character classes of plain ranges from U+0001 to U+FFFF, each leaving out `/` and the letters it must in both cases. They match every child but the allowed ones, including children made after the scan. They are in the call's settings file, which `--settings` names (it takes a file's path), so the command stays short. A browser's root shares one set of rules among its profiles that have the names Chromium gives (`root/Default/...`, `root/Profile */...`, `root/Guest Profile/...`, `root/System Profile/...`), so 84 profiles in one root cost about what one does, and a profile of such a name made after the scan is covered too. A profile elsewhere (an Electron app's data folder, a `--user-data-dir` profile named `Work`) has a set of its own.
    - **The by-name rules stay as a second wall,** in every profile and anywhere: the stores' own names (`Login Data`, `Bookmarks`, `IndexedDB`, `places.sqlite`, `key4.db`, `storage/default` and the rest), each database with its `-journal`, `-wal` and backup siblings, and the names that are also ordinary names (`Sessions`, `Shortcuts`, `Favicons`, `DIPS`) at any depth below where Chromium browsers keep their profiles (`User Data`, `Opera Software`, a Mac's `Application Support`) and in profiles Chromium names (`Default`, `Profile *`, `* Profile`) anywhere.
    - **Not covered:** a profile created after the scan, or one whose markers the scan didn't see (a folder it couldn't read), outside the default roots and outside a Chromium root's profile names, is covered by the name rules only. (A profile on a drive that wasn't scanned isn't readable at all.) So are a profile on a path no rule can start from (a share) and a Firefox fork's profile without Firefox's markers. A folder on the way down to a profile whose name isn't plain letters, digits, spaces, `.`, `_` and `-` hides that profile whole, caches included. Caches nested inside a hidden child (a cache in `Storage/ext/...`) stay proposable by the rules but hidden from Claude.
  - **password managers and wallets:** 1Password, Bitwarden, KeePass `.kdbx` files and crypto wallets.

  Messages and mail are not hidden; Zach chose that.

  Every rule built from a real path is a literal or fails safe, deny and allow rules alike: moved Claude Code and Codex folders (as set and as resolved), the fixture folder and drive roots. Claude Code doesn't escape rules you write yourself, and its matcher (the `ignore` package, 7.0.5 in Claude Code 2.1.309) can't spell every name:
  - **Spelled exactly:** a name whose characters are all printable ASCII other than `\`, `?` and `*`. A backslash goes before `[`, `]`, `{`, `}`, `!` and `#`, and before a trailing space; the matcher escapes the rest itself.
  - **Never spelled:** line breaks, CR, tab and every other whitespace, a Unix backslash, `?`, `*`, letters beyond ASCII and control characters. No allow rule is made for such a path. A deny rule writes `*` for each run of them, so it hides the folder and maybe a sibling, never less.
  - **No rule at all:** a path that isn't Unicode, or a moved folder on Windows that isn't from a drive letter. Then privacy mode off can't let Claude open files: every call runs as if privacy mode were on, and the panel and each answer say why. In fixture mode, a fixture folder no allow rule spells exactly refuses privacy mode off.
  - **Named places:** each rule is given twice (`//**/x` and `//*/**/x`), because the matcher's leading `**` stops at a line break in a folder's name.
  - **Proof:** a differential test (`crates/vacancy-core/tests/rule_matcher.rs`, through `tools/rule-matcher.mjs`) runs every kind of rule, for over a hundred adversarial names in Windows' and Unix's path styles, through `ignore` 7.0.5 and 5.3.2, with the scanned-drive rules (a profile on another drive denied, a Mac's `/` against `/Volumes/X`, a drive mounted in a folder, and files under a disk image or VHD mounted inside the scanned drive, nested mounts and mounts with odd names denied while files beside them stay allowed), the check's own settings and a root's shared profile rules among them. It prepares each rule as Claude Code 2.1.309's code does (read from its installed program, not a live call). It checks that each deny rule matches its target, and that each allow rule matches inside its root and nothing beside it, except a sibling spelled like the root in other case (the known limit below).
  - **The tested version:** the rules were verified against Claude Code 2.1.309, which bundles `ignore` 7.0.5. When Claude Code updates its matcher, the model in `tools/rule-matcher.mjs` (which `ignore` it bundles, and how it prepares a rule) needs rechecking. At runtime, the check below shows each Claude Code takes the settings at all.
  - **Known limit, case-sensitive Mac volumes:** the matcher compares case-insensitively, so an allow rule also covers a sibling folder whose name differs from its root only in case. On a case-sensitive Mac volume in fixture mode with privacy mode off, the fixture folder's allow rule therefore also lets Claude read such a sibling. Zach accepted this: it happens in fixture (test) mode only, and normal mode's allow rule is the scanned drive's root. (The rules for a scanned `/Volumes/X` compare the same way, but `/Volumes` is on the startup disk, case-insensitive by default, so macOS mounts a second volume called `x` as `x 1`.) (A deny rule matching other case only hides more.)

  `--add-dir` takes paths, not patterns, and is never escaped. A real probe showed a `[work]` folder denied as spelled, for Read, Glob and Grep (`docs/proof/t12-glob-probe/`).
- **A check of each Claude Code before it reads (Zach's decision).** A `-p` call ignores a settings file it rejects without a word, and Vacancy's own check of its settings can't prove a later Claude Code takes them. So before the first privacy-off answer from an executable, Vacancy makes one small real call (`claude::canary`):
  - **The folder:** a fresh throwaway folder in the app's data folder (`claude-check/check-...`), outside anything of the user's, removed after the call. It holds a control file and a dummy Chromium profile (`BrowserData/Work`, with `Preferences` and `History` markers and a `Local State` above it) whose `Sessions/Session_1` is the canary. Both files hold fresh random words each time; the prompt names the files, never their words.
  - **The call:** built exactly as a privacy-off call, by the same builder: the settings in a file, the same flags and environment, `blockReadsOutsideWorkingDirectories`, no `--model`, and the folder as the read scope (as a drive, with the drive list's other drives and every mount point, or in fixture mode as the fixture folder is). The folder is scanned, so the canary is hidden by the browser-profile rules a real scan makes. Claude is asked to Read both files and give what it read, in a strict JSON schema. It costs one small call per Claude Code update.
  - **Passed** only when the control's words came back, the canary's didn't, and Claude Code refused the canary's read (its JSON output lists refusals; when it lists none at all, the control's presence and the canary's absence decide). Anything else (the canary read, the control missing, another refusal, an error, a timeout, an answer that doesn't parse) isn't: every call runs as if privacy mode were on, each answer's text says why, and the panel's privacy row says Vacancy couldn't verify this version of Claude Code, with Check again.
  - **Kept** in the app's data folder (`claude-check.json`), keyed by the executable's resolved path, size, modified time and `claude --version`; a change to any of them makes the check due again. Its version is asked again whenever the file changes, and on Check again. A check that was cancelled, or found Claude Code gone or signed out, isn't kept.
  - **When:** when the person turns privacy mode off, at the first privacy-off call (or chat) if it is still due, at start with Claude on and privacy mode off if it is due, and on Check again. The privacy row says "Checking Claude Code…" meanwhile.
  - **What it proves:** this Claude Code honours Vacancy's settings file, and with it the browser-profile deny rules and the read scope. **What it doesn't:** that every rule on its own means what it says; the differential test does that against the matcher (`tests/rule_matcher.rs`, which runs the check's own settings too). Proof with Claude Code 2.1.309: `docs/proof/t12-canary-check/`.
- **Chats keep their mode, and a change of mode ends them.** The core keeps every chat, per scan, by an id it gives out; the UI sends only that id and the person's new question. A chat's first answer can come before its id does; its follow-ups wait for the id, so a follow-up never opens a second chat. A chat holds the privacy mode it began in, and each of its turns the mode it was made in. Changing privacy mode, or turning Claude off, ends every chat in the core in the same step as the new setting is kept (a request is prepared wholly before or wholly after). The panel ends its own and asks nothing until the core has answered. A question to an ended chat, or one in the other mode, is refused and sends nothing; the panel asks it again in a new chat. So a call with privacy mode on never holds a chat turn from privacy mode off. It sends Claude's items made with privacy mode off by their name in the scan only, never with Claude's note about them.
- **Still sent either way:** Vacancy's prompt and Claude's replies, and the account email Claude Code itself adds. Zach has zero data retention on.
- **A risk accepted with privacy mode off:** a file Claude reads can carry text meant to steer it. That is safe because Claude can't act, the Guard still applies, and its items start unticked behind the user's one confirmation.

## States

The advisor shows one of these states:

- **Not found:** no `claude` was found. Vacancy looks in `%USERPROFILE%\.local\bin\claude.exe` and the PATH on Windows, and `~/.local/bin/claude`, Homebrew and npm global plus the login shell's PATH on macOS. It spawns the `.exe`, never a `.cmd`.
- **Not signed in:** `claude auth status` fails.
- **The sign-in check timed out, or failed:** `claude auth status` didn't answer in 30 seconds, or couldn't run. Each shows its own state with why; neither is shown as "not signed in".
- **Off, on, working:** working can be cancelled, and slow shows after a while.
- **Timed out, and error:** each with Claude's message.
